# 档案页面图表方案详细说明

## 一、先说结论

当前项目档案页面里使用的图表方案，不是直接手写的原生 JS 图表，也不是 ECharts，而是 `qiun-data-charts`。

更准确地说：

- 页面层直接接入的是 `qiun-data-charts` 组件
- `qiun-data-charts` 底层属于 `uCharts` 图表体系

所以如果有人问“档案页图表是不是 uCharts”，答案是：

- 是
- 但不是直接裸用 `uCharts`
- 而是通过 `qiun-data-charts` 这个 uni-app 组件封装在使用

## 二、当前项目中的实际落点

下面是当前仓库里能直接定位到的图表使用位置。

### 1. 档案页折线图

- 文件：`pages/GrowthArchive/components/ArchiveTrendCard.vue`
- 形式：`<qiun-data-charts />`
- 用途：展示档案页的趋势变化数据

这个组件主要承担“成长趋势”这一类信息可视化，重点不是复杂交互，而是把一段时间内的数据走势直观展示出来。

### 2. 档案页雷达图

- 文件：`pages/GrowthArchive/components/AIJobGapCard.vue`
- 形式：`<qiun-data-charts type="radar" />`
- 用途：展示能力维度、岗位要求差距、雷达型评估结果

这个组件更偏“能力结构”展示，把多维度信息放在一个图里，适合做“我当前水平”和“目标岗位要求”的对比。

### 3. 测试页中的雷达图示例

- 文件：`subPages/searchTest/searchTestResult.vue`
- 形式：`<qiun-data-charts type="radar" />`

这个页面更像是一个实验或测试入口，可以帮助我们确认项目里雷达图同样走的是 `qiun-data-charts / uCharts` 这一套，而不是其他图表库。

## 三、为什么会选用 uCharts / qiun-data-charts

这个问题不能只从“图表效果好不好看”来判断，真正影响技术选型的通常是下面几类因素：

- 项目框架是不是 uni-app
- 页面是不是要兼容 H5 / 小程序 / App
- 图表复杂度高不高
- 后续维护成本大不大
- 团队是否需要快速交付

对于当前这个项目来说，使用 `uCharts / qiun-data-charts` 是比较合理的选择。

### 1. 它更适合 uni-app 的多端运行环境

当前项目不是纯 H5 项目，而是 uni-app 项目。uni-app 的一个核心特点是：

- 同一套页面结构可能运行在 H5
- 也可能运行在小程序
- 也可能运行在 App WebView 环境

这就意味着图表方案不能只考虑“浏览器里能不能画出来”，还要考虑：

- 多端表现是否一致
- 触摸事件是否稳定
- canvas 渲染是否容易出兼容问题
- 页面切换、重新进入后是否容易异常

`uCharts` 这类方案本身就是围绕 uni-app / 小程序 / App 场景成长起来的，所以天然更适配这一类工程。

如果自己用纯 JS 写图表，通常一开始是在 H5 看起来没问题，但一到小程序或 App 环境就会出现更多适配细节，后面会越来越重。

### 2. 它的接入方式非常贴合 uni-app 组件开发

在当前项目里，图表不是以“自己 new 一个图表实例”的方式接入，而是像普通组件一样直接写在模板里：

```vue
<qiun-data-charts type="line" :opts="opts" :chartData="chartData" />
```

这种方式带来的好处是：

- 更符合 uni-app / Vue 的组件化思路
- 数据和视图关系更直接
- 页面结构清晰
- 更容易跟随 `props`、`computed`、`data` 一起维护

如果自己用 JS 去写，往往要多处理一整套额外问题：

- 获取 canvas 节点
- 初始化图表实例
- 页面 mounted 后再绘制
- 数据变化时手动更新
- 页面销毁时手动释放
- 页面尺寸变化时重算布局

这些事情不是做不到，而是对业务开发来说性价比不高。

### 3. 当前业务图表复杂度并不高，uCharts 已经够用

档案页现在主要是两类图：

- 折线图
- 雷达图

这两类图在业务系统里都属于常见基础图表，不是高复杂度图形。

当前页面的图表目标更偏向：

- 让用户快速看懂趋势
- 让用户快速理解自己的维度结构
- 为成长档案页面增加可视化表达

而不是：

- 做海量数据分析
- 做专业 BI 看板
- 做几十种交互联动
- 做极度复杂的图层渲染

在这种前提下，`uCharts` 提供的能力已经足够支持当前业务，不需要为了“理论上能力更强”而引入更重、更复杂的方案。

### 4. 它的维护成本明显低于手写 JS 图表

图表不是“画出来就结束了”，后续长期维护才是成本真正高的地方。

如果自己用原生 JS 或 canvas 手写一套图表，后面通常要不断维护这些内容：

- 坐标轴绘制
- 刻度计算
- 标签重叠问题
- 图例布局
- 数据点高亮
- tooltip 提示
- 动画过渡
- 触摸滑动交互
- resize 重绘
- 高清屏像素比处理
- 主题切换
- 页面销毁与重建

而 `qiun-data-charts` 已经把这些通用能力封装成组件能力，业务代码更关注：

- 数据来源是什么
- 图表展示哪几个维度
- 样式参数怎么调

这会让后续维护的重心落在业务层，而不是落在图表底层实现上。

### 5. 对移动端项目来说通常更轻量

对 uni-app 项目来说，图表库不只是“能不能用”，还要考虑：

- 包体大小
- 首屏加载速度
- 移动端渲染压力
- 小程序端性能表现

相较于一些更偏 Web 大屏、BI、复杂分析场景的图表库，`uCharts` 往往更轻一些，也更符合移动端业务页面对性能和包体的要求。

对档案页这种场景来说，用户重点是“顺畅浏览信息”，不是“做复杂数据分析”，因此轻量方案通常更合适。

## 四、为什么不直接用原生 JS 手写图表

“用 JS 写图表”听上去灵活，但它的问题在于：灵活的另一面通常就是高维护成本。

### 1. 原生 JS 图表的优势

先说优点，直接手写并不是没有意义。它适合：

- 图表样式极其定制化
- 交互非常特殊
- 只针对某一个平台，比如只做 H5
- 团队里有人愿意长期维护图表底层

在这种情况下，自己写可以做到完全掌控。

### 2. 但当前项目不属于这种类型

当前档案页图表的特点是：

- 图表类型常规
- 场景偏业务展示
- 项目是 uni-app 多端项目
- 需要的是稳定和快速交付，而不是极限自定义

所以如果强行自己写，最终很可能会出现一种情况：

- 前期投入比组件方案更高
- 后期维护比组件方案更累
- 产出的业务价值却没有明显更高

换句话说，不是不能写，而是没必要在这个场景下自己造轮子。

### 3. 在 uni-app 中自己写图表的实际麻烦点

如果在 uni-app 里完全自己做一套图表，通常会遇到这些现实问题：

- 不同平台 canvas 行为差异
- H5 与小程序绘制表现不完全一致
- 触摸坐标换算麻烦
- 页面显示区域变化后要自己重算
- 局部刷新与整图重绘策略要自己定
- 组件复用时边界情况变多

这些都不是单次开发能解决完的，而是会在后续维护中持续出现。

## 五、为什么不是 ECharts

你之前提到“记得自己用的是 ECharts”，这个感觉其实很常见，因为很多人会把“所有图表”都习惯性叫成 ECharts。

但就当前这份仓库代码来说，档案页里没有搜到 ECharts 的使用痕迹，实际就是 `qiun-data-charts`。

### 1. ECharts 并不是不能用

ECharts 本身非常强，优点很多：

- 图表种类丰富
- 可配置项非常多
- 社区成熟
- Web 端生态强
- 复杂图表能力强

如果是纯 H5 后台、数据分析平台、大屏看板、复杂联动场景，ECharts 反而经常是更自然的选择。

### 2. 但 ECharts 的强项不一定是当前场景最需要的

当前档案页并不需要：

- 很多图联动
- 海量配置项
- 极复杂数据分析能力
- 高度专业的数据可视化控制台

它更像一个移动端成长档案页面，重点是：

- 快速展示
- 用户能看懂
- 页面流畅
- 多端稳定

这时 `uCharts / qiun-data-charts` 的“更轻、更贴近 uni-app、多端更省心”这几个点，通常比 ECharts 的强大能力更有价值。

### 3. 从团队协作角度看也更稳

如果团队里大多数 uni-app 页面都偏向组件式开发，那么用 `qiun-data-charts` 会让图表页看起来和普通页面开发方式一致。

这会带来两个现实好处：

- 新同学接手更容易
- 后续维护更统一

而不是把某个业务页单独变成一套完全不同的图表工程。

## 六、从当前业务场景看，uCharts 为什么更合适

如果只针对“成长档案页”这个具体页面来说，使用 `uCharts / qiun-data-charts` 的适配性可以概括成下面几点。

### 1. 图表只是页面的一部分，不是页面主体

成长档案页本质上还是一个信息整合页，除了图表外，还有：

- 个人档案信息
- 分析说明
- 结果卡片
- 文案内容
- 操作入口

也就是说，图表在这里是“增强表达能力”的模块，而不是整个页面的唯一核心。

这种页面更适合选择一个稳定、轻量、集成方便的图表方案，而不是为了图表本身引入过重的技术栈。

### 2. 折线图和雷达图都属于成熟基础能力

当前档案页的图表类型非常标准：

- 折线图看趋势
- 雷达图看维度

这两种图在 `uCharts` 里都属于成熟支持能力，不需要特别复杂的二次封装。

### 3. 业务关注点在数据解释，不在图形炫技

这个页面更重要的是：

- 趋势是否准确
- 维度是否清楚
- 用户是否一眼能理解

而不是：

- 图表能不能做超级复杂的视觉特效
- 能不能做非常重的分析型联动

所以一个够用、稳定、成本低的方案，反而更符合业务价值。

## 七、如果以后要换方案，什么时候可以考虑 ECharts 或手写 JS

虽然当前选型合理，但不代表未来永远不能变。

下面这些场景，可以重新评估是否要换成 ECharts 或自定义图表方案：

- 需要更多复杂图表类型
- 需要大量联动交互
- 需要更强的动画表现
- 页面只跑 H5，不再强调 uni-app 多端统一
- 设计稿对图表定制要求非常高
- 业务方要求接近 BI、专业分析平台的能力

如果未来出现这些需求，ECharts 或自定义绘制就有可能更合适。

但至少从当前这份代码、当前档案页场景来看，`qiun-data-charts / uCharts` 仍然是一个更平衡的方案。

## 八、最终总结

可以把这次结论浓缩成下面几句话：

- 当前档案页面的折线图和雷达图，实际使用的是 `qiun-data-charts`
- `qiun-data-charts` 底层属于 `uCharts` 体系
- 它之所以被选用，不是因为它在所有场景都最强，而是因为它更适合 uni-app 的多端业务项目
- 相比自己用原生 JS 手写图表，它接入更快、兼容更省心、维护成本更低
- 相比 ECharts，它在当前这种移动端业务图表场景下通常更轻、更实用、更符合项目实际需求

一句话总结就是：

当前档案页选用 `qiun-data-charts / uCharts`，核心优势不在于“图表能力最强”，而在于“在 uni-app 多端业务场景下更省心、更稳定、成本更合适”。
